　01　本周学习笔记　

本周正式进入编码阶段，学习内容围绕“怎么把 FastAPI、SQLModel、JWT、消息总线这些零件拼成一个可扩展的工程骨架”展开，同时深入实践了黑板模式、注册表模式与检查点持久化，为后续九个 Agent 的并行开发铺路。

1.1 FastAPI 分层与依赖注入

●　APIRouter 分模块注册：auth、items、market、negotiation、orders、social、moderation 各占一个路由文件，由 api 包统一汇总，避免入口文件膨胀。

●　lifespan 管理生命周期：建表、跑种子、初始化检查点、绑定事件循环、引导注册 Agent 全部在 lifespan 中按序完成，关闭时再释放检查点资源。

●　依赖即鉴权：用 Depends(get_current_user) 把“当前用户从哪来、是否冻结、角色是否匹配”收口成一个依赖，接口只声明需要什么角色。

1.2 SQLModel + SQLite WAL 实战

●　模型即表：SQLModel 兼具体检 Pydantic 与 ORM 能力，一套模型既做接口 Schema 又做数据库表，字段类型注解直接驱动建表。

●　统一同步访问：鉴于 SQLite 与演示场景，数据访问统一走同步引擎（WAL 提升并发），避免同步/异步 session 混用阻塞事件环。

●　外键与枚举：外键用 foreign_key 声明，状态用 StrEnum 落库，种子脚本幂等执行（先查后插），反复初始化不产生脏数据。

1.3 JWT + bcrypt 认证机制

●　口令只存哈希：注册时 bcrypt 加盐哈希，数据库中不保留任何明文口令；登录用 bcrypt 校验，错误口令统一返回 401。

●　无状态 JWT：登录成功签发携带 user_id 与角色的 JWT，后续请求走 Bearer Token；过期或伪造令牌在依赖层拦截。

●　冻结不等于注销：被冻结账号禁止任何交易动作但保留申诉入口，对应需求中“冻结账号禁止交易但可申诉”。

1.4 黑板模式与 Reducer 写纪律

●　单一事实源：黑板由 LangGraph 类型化 State 承载，商品池、会话、订单、冲突事件、Agent 健康位都只允许通过 reducer 写入。

●　私有状态可纠偏：Agent 可以缓存私有视图，但每次行动前与黑板比对；不一致即以 SSOT 为准自动纠正并记录偏差来源（C7）。

●　消息不留共享可变状态：Agent 之间只通过 ACL 消息传值，不允许互相持有对方的可变对象，从规范上消灭隐式耦合。

1.5 发布订阅总线与注册表模式

●　事件总线：基于 asyncio 的发布订阅总线把消息分发与业务处理解耦，总线按 conversation_id 投递，总线本身不做业务判断。

●　注册表即“通讯录”：Agent 启动时向注册表登记名字与能力，协调者按名字解析目标；新增 Agent 只需登记，协调核心零改动（AC-9）。

●　熔断有处可依：注册表同时维护健康位，Agent 被熔断后协调者可把它的职责临时收回代管，恢复后再交还。

1.6 检查点持久化与轨迹查询

●　SQLite Saver：接入 langgraph-checkpoint-sqlite，按 graph_thread_id 保存每个超级步的状态快照，与业务库分离为 checkpoints.db。

●　轨迹是答辩资产：一次议价或仲裁结束后，可按线程拉取逐步消息、结论、置信度与升级路径，决策回放就是最好的可解释证据。

1.7 幂等种子数据工程

●　一键还原演示环境：种子包含含 2400320321 在内的买卖账号、管理员、多类目商品、历史成交价与初始信用分，启动即得可演示数据集。

●　幂等设计：所有种子先按自然键查询再插入，重复执行 lifespan 不会产生重复账号或商品。

1.8 HTTP 请求的分层穿透与横切关注点

●　一次请求八步穿透：浏览器 → APIRouter → deps 鉴权 → Agent/Graph → kernel/DB，再沿原路返回；把链路画成泳道图后，鉴权、业务、持久化的边界一目了然。

●　横切关注点统一下沉：CORS、统一异常处理、trace_id 结构化日志不属于任何业务模块，集中在中间件与依赖层实现，避免业务代码里到处复制 try/except。

●　启动也是一条流水线：lifespan 中“建表 → 种子 → 检查点 → 总线 → 子图 → Agent 注册”严格有序，前一步失败即快速中止，杜绝“半启动”的不确定状态。

2.4 注册登录与角色鉴权

完成注册、登录接口与 JWT 依赖：正确口令获得令牌，错误口令 401，越权访问管理员接口 403，冻结账号在依赖层被拦截并引导申诉；种子账号可直接登录，为前端联调做好准备。

app/api/deps.py（JWT 鉴权依赖）

def get_current_user(token: str = Depends(oauth2_scheme),

session=Depends(get_session)) -> User:

try:

payload = jwt.decode(token, settings.secret_key, algorithms=["HS256"])

user_id = int(payload["sub"])

except JWTError:

raise ApiError(401, "E-001", "登录凭证无效或已过期")

user = session.get(User, user_id)

if not user:

raise ApiError(401, "E-001", "用户不存在")

if user.status == UserStatus.FROZEN:

raise ApiError(403, "E-002", "账号已冻结，可发起申诉解冻")

return user

class AgentRegistry:

def __init__(self):

self._agents: dict[str, BaseAgent] = {}

def register(self, agent: BaseAgent) -> None:

self._agents[agent.name] = agent # 启动即登记

def resolve(self, name: str) -> BaseAgent:

agent = self._agents.get(name)

if agent is None:

raise ApiError(503, "E-503", f"Agent 未注册：{name}")

if self.is_fused(name): # 熔断中 → 协调者代管

return self._agents["coordinator"]

return agent

　03　存在的问题　

骨架跑通后，进入多模块并行开发前仍有以下问题需要处理：

●　问题 1　黑板 reducer 粒度待细化：当前黑板按整块字典合并，后续议价轮次高频更新时需要按字段设计合并函数，避免消息列表相互覆盖。

●　问题 2　同步引擎的吞吐上限：统一同步 SQLModel 简化了开发，但 WebSocket 长连接下可能占用工作线程，需要压测确认是否引入连接池大小限制。

●　问题 3　检查点与业务库的数据一致性：状态快照在 checkpoints.db、业务事实在 campus_mas.db，两库不跨库事务，极端崩溃下要以业务库为准做恢复。

●　问题 4　种子口令的演示安全：种子账号使用固定弱口令便于答辩登录，需要在文档与登录页显著标注“仅为课程演示数据”。

●　问题 5　异常码还需补全：本周认证与内核场景又新增 E-001/002/503，通信与超时类编码要在下轮统一回表更新。

●　问题 6　JWT 续期策略未定：目前令牌过期需重新登录，议价中途过期体验较差，计划用较长有效期 + 关键操作二次确认过渡。
