一 引言

▍1.1 编写目的

本计划是“校园二手交易平台 Multi-Agent 系统”项目的风险管理基准文件，依据《软件需求规格说明书 V4.0》（以下简称 SRS V4）确定的范围、技术选型、验收标准与 WBS 任务队列（T1–T32）编制，目的在于：系统识别项目全周期可能影响 P0 目标（完整交易旅程、9 类 Agent、三级冲突机制、8 类冲突场景、≥10 个剧本、15 条验收标准）达成的不确定性；给出统一的概率—影响评估标准与风险等级；对每项风险预先安排预防措施、应急计划、责任人和触发指标；建立周度监控与升级机制，确保风险被尽早发现、按级响应、闭环留痕。

▍1.2 项目概述

二 风险管理组织与职责

本项目为单人团队，风险管理实行“开发者首责、导师升级”的精简模式：风险责任人统一为开发者本人；高等级风险及跨范畴决策在周报中专题上报指导教师评审。

角色 人员 风险管理职责
项目经理 / 开发者 梁奕琦 维护风险登记册；执行风险识别、概率影响评估、应对措施落地与周度复盘；监控触发指标；风险发生时启动应急预案并记录闭环结果
指导教师 曾志新 评审高风险项与研究核心相关风险（R-04 等）；对进度裁剪、方案降级等重大权衡做方向裁决；提供技术与资源咨询
评审机制 — 每周周报固定检查“风险状态”小节；里程碑节点（M1–M9）进行专项风险评审并决定是否进入下一阶段

三 风险管理流程

项目采用五阶段闭环流程，覆盖从识别到闭环的全过程，并与周报、里程碑评审节奏绑定：

阶段 活动 输入 / 输出 频率 / 时点
① 风险识别 对照 SRS 功能/非功能需求、WBS 任务依赖、技术选型假设，按技术、进度、质量、安全、研究、环境、管理七类枚举风险 SRS V4、WBS、周报 → 风险登记册新增条目 计划期集中识别；每周增补
② 风险评估 按第四章标准打分：风险值 = 概率 P × 影响 I（各 1–5 级），确定高/中/低等级 风险描述 → P、I、等级、近因与征兆 识别即评估；状态变化时重评
③ 应对规划 从规避 / 减轻 / 转移 / 接受四种策略中择策；编写预防措施、应急计划、触发指标与关闭标准 等级 → 应对策略 + 预案 + 责任人 评估后 2 日内
④ 风险监控 跟踪触发指标与任务进展；中风险周查、高风险每三天关注；检查缓冲消耗 指标数据 → 登记册状态更新 持续；周报固定复盘
⑤ 响应与闭环 风险触发即执行应急预案；高风险同步上报导师；处置后验证效果、归档经验并关闭条目 触发事件 → 应急记录 → 闭环结论 触发即启动

应对策略定义：规避＝改变方案使其不发生（如调整范围、更换技术）；减轻＝降低概率或影响（本项目主要策略）；转移＝将影响交由外部承担（本项目仅适用于选择成熟框架/库）；接受＝对低风险或无更优手段者预留储备、自行承担。

四 风险评估标准

▍4.1 概率分级（P）

等级 定性描述 参考概率 本项目判据示例
5 几乎必然 ≥80% 单人承担、历史项目同类问题反复出现
4 很可能 60%–80% 依赖不成熟能力或外部不稳定服务，无现成实践
3 可能 30%–60% 技术可行但复杂度较高、首次实现
2 不太可能 10%–30% 有成熟方案或已做预研，仅剩执行偏差
1 罕见 <10% 常规工程问题，工具链完善

▍4.2 影响分级（I）

等级 进度 质量 / 验收 演示与研究目标
5 关键路径延期 >5 天 AC 验收不通过 / P0 范围缺失 现场无法演示或研究核心结论不成立
4 延期 3–5 天 关键 rubric 评分 <4 核心剧本失败、需大幅临场解释
3 延期 1–3 天 非关键功能缺陷，可绕行 部分 P1 效果受损
2 延期 <1 天 表面缺陷，不影响功能 素材/体验小瑕疵
1 无影响 当天可修复 几乎不可感知

五 风险登记册（共 18 项）

风险编号规则 R-XX；“关联”列引用 SRS 的 FR/NFR/AC 编号与 WBS 任务号；等级颜色：红＝高、黄＝中、绿＝低。风险值截至 2026-10-13 的事前评估，将在每周复盘中动态更新。

编号 类别 风险描述（含关联项） P I 等级 策略 预防措施 / 应急预案 监控触发指标
R-01 技术

大模型依赖风险：DeepSeek API Key 缺失、限流、超时或返回非法 JSON，导致意图/审核/议价/仲裁链路中断

关联：NFR-6 AC-8/12；T6

 4 3 中 减轻

预防：①结构化输出→Pydantic 校验→最多 3 次重试→RuleLLM 确定性兜底；②单轮超时 3 秒；③默认 Mock 模式，界面可切换 LLM；④关键动作强制人工确认

应急：立即切 RuleLLM 全量兜底保证演示不中断；记录故障样本，事后补跑；必要时转人工处理

 LLM 调用失败率>10% 或 P95>3s；连续 2 次非法 JSON
R-02 技术

LangGraph 1.x 新版本学习曲线与 API 变动风险：Checkpointer/interrupt/条件边为研究核心依赖，理解偏差会拖垮内核

关联：T5/T7/T8/T20

 3 4 中 减轻

预防：①锁定 langgraph 1.2.x 并写入 requirements 锁定文件；②编码前做最小 Spike 验证图编排+检查点+人工回环；③仅使用官方文档稳定特性

应急：回退到已验证版本；用最小复现用例定位问题并向导师/社区求助；极端情况下以手写状态机承载主图

 Spike 超时未通；版本升级出现破坏性变更
R-03 技术·质量

并发抢单一致性风险：预占锁/乐观版本/超时回滚实现缺陷，出现超卖或脏状态（AC-3 硬性二元验收）

关联：NFR-2 AC-3；T14

 3 5 高 减轻

预防：①锁令牌+乐观版本号+超时点三件套先于业务实现；②SQLite WAL；③asyncio 并发测试用例先行（两路并发恰一成功）；④非法状态迁移一律拒绝

应急：对下单临界段串行化兜底；立即回滚释放锁并恢复商品“在售”；用种子数据重建受影响订单

 并发测试出现任何超卖/双成交；锁超时未释放
R-04 研究核心

冲突决策机制效果不达预期：效用权重（0.25/0.20/0.30/0.15/−0.10）、纳什参考价与票权均为经验初值，剧本裁决可能不合理

关联：第六章；T18–T20/T30；AC-4/5

 4 4 高 减轻

预防：①全部参数配置化并保证同输入同输出可复现；②≥10 个剧本含期望对照表逐案校准；③T30 权重对比实验支撑取值论证；④指导教师参与参数评审

应急：按剧本结果回调权重并留档；对争议场景降级为确定性规则裁决；在论文中如实说明参数局限性与敏感性

 剧本断言通过率<90%；同一冲突两次裁决不一致
R-05 进度

单人开发进度风险：32 项任务、前后端+内核+测试全栈，且与期末其他课程考试冲突，关键路径无冗余人力

关联：全局；M3–M8

 4 4 高 减轻

预防：①WBS 拆成可独立交付的纵向切片，严格按依赖波次推进；②P0/P1 物理隔离，P1 不进关键路径；③每周预留 1 天缓冲；④每波设定退出标准，不通不扩面

应急：按 P1（T27/T30/T32）→非关键 FR 的顺序裁剪；启用 12/24–12/30 集成缓冲；向导师申请延期演示彩排

 任一里程碑实际偏差>3 个工作日；缓冲累计消耗>50%
R-06 管理

需求蔓延风险：开发中临时增加功能（真实图片审核、更多 Agent、新页面），侵蚀 P0 工期

关联：SRS 3.4；Q1–Q5

 3 3 中 规避

预防：①以 SRS V4 为冻结基线，新增想法一律记入“变更候选”不当场开发；②坚持明确不做清单（真实支付/物流/统一认证/App/集群）

应急：变更走简易评审：评估对 AC 与关键路径影响，默认排入下学期，至多以配置项形式预留

 出现未经评估即动工的新需求；周计划外工时占比>15%
R-07 技术

三级人工回环实现风险：LangGraph interrupt 挂起/恢复、冻结订单商品、裁决写回 SSOT 链路复杂，易产生悬挂状态

关联：AC-5；T20/T26

 3 4 中 减轻

预防：①在 T8 主图阶段即引入最小 interrupt 演练；②冻结/恢复动作配套检查点轨迹测试；③工作台终裁写回采用幂等设计

应急：工作台增加轮询补偿与“手工恢复”入口；编写悬挂事务核查脚本；极端情况按检查点重建图状态

 挂起事件无法恢复；终裁后状态未流转
R-08 技术

议价 WebSocket 实时一致性风险：出价乱序、倒计时漂移、断线重连后会话丢失

关联：FR-6 NFR-3；T22

 3 3 中 减轻

预防：①会话状态以服务端为权威，客户端只渲染；②单调让步违例拒收、轮次/时间服务端计时；③断线重连拉取全量出价序列

应急：WS 异常时降级为 HTTP 短轮询；保留议价记录事后重放

 WS 测试出现乱序/重复消息；重连后序列缺失
R-09 安全

安全机制被绕过风险：JWT/角色守卫配置疏漏、数据未按用户隔离、veto 被投票或效用逻辑覆盖

关联：NFR-4 AC-1；T4/T11

 2 5 中 规避

预防：①bcrypt 哈希+JWT 校验+买家/卖家/管理员三级守卫+冻结拦截；②veto 在服务端硬判定，任何上游放行不可覆盖并编写对抗调用测试；③接口级越权测试全覆盖

应急：发现绕过立即修复并回归全部安全剧本；冻结可疑账号；审计日志回溯影响面

 对抗测试出现 veto 放行；越权接口返回 200
R-10 进度·质量

前端工程量风险：卖家/买家/管理员三端页面众多，联调滞后可能导致 AC-13 rubric 与 E2E 演示不达标

关联：AC-13/2；T23–T26

 3 3 中 减轻

预防：①Element Plus 统一布局与组件复用；②API 契约先行，前端基于 Mock 并行开发；③按用户旅程逐页走查截图

应急：优先保三端主流程完整，视觉效果做减法；P1 大屏资源不足时直接裁剪

 T24/T25 启动时 API 仍不可用；走查缺陷>15 个
R-11 环境·可复现

干净环境一键启动失败风险：Windows + Python/Node 版本差异、依赖安装失败，导致 NFR-7 与现场演示翻车

关联：NFR-7；T31

 3 4 中 减轻

预防：①提供 Windows 一键启动脚本（后端+前端+初始化+播种）；②依赖版本锁定；③在全新目录按 README 做第三方视角走查

应急：准备第二套已验证环境（笔记本）；离线录屏与截图兜底；现场优先使用无 Key Mock 模式

 全新环境走查任一步骤失败；演示彩排启动超时
R-12 质量

剧本与故障注入覆盖不足风险：C1–C8 映射遗漏、≥10 剧本数量不足或断言不严，AC-7/AC-12 无法取证

关联：AC-7/12；T28/T29

 3 3 中 减轻

预防：①建立 C1–C8→剧本→断言映射表，剧本随功能任务同步编写；②非法 JSON/超时/无 Key 三类故障注入用例化；③纳入回归集

应急：缺口用手工演示脚本与录屏补充证据；冻结期集中补齐剧本

R-13 质量·研究

内容审核误判/漏判与可解释性不足：规则库覆盖有限，审核结论依据不充分导致 TR-11.2 rubric<4

 3 3 中 减轻

应急：低置信度一律转人工复核；扩充违禁词表并重跑样本评审

 样本评审 rubric<4；出现违禁漏判
