　01　本周学习笔记　

本周围绕“让 Agent 真正聪明起来又不失控”学习：系统实践了面向结构化输出的提示词工程、意图识别与槽位填充、规则与模型双路审核，掌握了 LangGraph 子图组合与条件路由，并把 Agent 统一收口到同一个基类契约下，为九个节点的并行开发建立规范。

1.1 面向结构化输出的提示词工程

●　系统提示词模板化：把角色定义、任务目标、输出 JSON Schema、3 个少样本示例固化进 system 消息，模型只负责“填表”，显著降低自由发挥。

●　低温与枚举约束：审核、议价等需要稳定结论的环节温度降到 0.2，并要求枚举字段只能取给定值，再经 Pydantic 二次校验。

●　错误回灌修复：校验失败时把具体错误信息（如“confidence 必须在 0–1”）拼进下一轮请求，让模型自我修复，比简单重试成功率更高。

1.2 意图识别与槽位填充

●　意图枚举封闭：用户自然语言先归到发布、搜索、出价、支付、申诉、闲聊六类意图之一，无法归类则发起澄清式追问而不是猜测执行。

●　槽位结构化：发布意图抽取类目、成色、价格、数量；出价意图抽取目标商品与金额；缺槽时向用户追问，槽位齐全才调用下游 Agent。

1.3 规则 + 模型双路文本审核

●　高召回与高准确分工：违禁词规则负责“宁可错杀”的高召回安全底线，模型语义判定负责理解隐晦表达的高准确判断，两路结论按置信度合并。

●　结论必须可解释：审核输出不是简单的通过/驳回，而是 decision + confidence + reasons[]，每条理由对应用户能看懂的说明，可在申诉界面直接展示。

1.4 基于历史成交价的分位数定价

●　区间而非定值：用同类目历史成交价的 P25–P75 分位数作为建议区间，再乘以成色系数修正，卖家可改价，Agent 不替用户拍板。

●　冷启动兜底：历史样本不足 5 条时退化为“卖家自填 + 文字提示”，避免用不可靠的统计数字误导。

1.5 LangGraph 图组合与条件路由

●　子图复用：发布流程、交易流程各成子图挂入主编排图，冲突处理做成可复用子图，节点之间只通过黑板状态通信。

●　条件函数即路由表：route_* 函数读取状态返回下一节点名（如审核后按 approve/reject/review 三分支），把复杂 if-else 从业务代码中抽离成显式的图边。

1.6 Agent 基类与能力声明

●　统一 handle 契约：所有专家 Agent 继承同一基类，入口都是 handle(envelope: AclEnvelope) -> AclEnvelope，协调者不需要知道节点内部细节。

●　能力自描述：每个节点声明 capabilities（能处理的意图/任务标签），注册表据此做任务匹配，新增节点不改协调者代码。

1.7 决策轨迹可观测

●　统一 traced 装饰器：在节点入口出口自动记录输入信封、输出信封、耗时与置信度，消息同步落 acl_messages，检查点与业务轨迹通过 thread_id 双向关联。

●　可解释是默认能力而非补丁：审核理由、出价依据、裁决书都随结论一起产生，不允许出现“只给结论不给依据”的黑盒节点。

1.8 槽位填充与双路置信度融合

●　意图—槽位两阶段：先做封闭枚举的意图分类，再按意图模板抽取槽位（title/condition/price/category）；槽位不齐时发起澄清追问，系统宁可多问一句也不猜测执行。

●　置信度是融合的货币：规则与模型两条通道各自输出置信度，融合规则按“安全优先、分歧转人工”设计：安全列恒否决，置信差 |Δ| < 0.15 时不强行裁决而转复核。

●　统计方法进入定价：学习了用分位数（P25/P75）而非均值给出建议价区间——均值对极端高价敏感，分位数带更能反映“正常成交价范围”，再用成色系数修正。

def moderate(title: str, desc: str, banned: list[str]) -> ModerationResult:

text = f"{title} {desc}"

hits = [w for w in banned if w in text]

if hits: # 规则通道命中 → 直接 veto

return ModerationResult(

decision="reject", confidence=1.0, veto=True,

reasons=[f"命中违禁词：{hits[0]}（规则通道，不可被投票覆盖）"])

if any(k in text for k in ("全新未拆", "九成新", "八成新")):

return ModerationResult(decision="approve", confidence=0.7,

reasons=["成色描述明确，规则通过"], veto=False)

return ModerationResult(decision="review", confidence=0.5,

reasons=["关键信息不足，转人工复核"], veto=False)

def price_band(history: list[float], condition: str) -> tuple[float, float]:

"""同类目历史成交价 P25–P75，再按成色系数修正。"""

if len(history) < 5: # 冷启动：样本不足不建议

return None

q1, q3 = percentile(history, 25), percentile(history, 75)

k = {"全新": 1.05, "九成新": 0.90,

"八成新": 0.75}.get(condition, 0.7)

return round(q1 * k, 2), round(q3 * k, 2)

▲ 安全底线在代码中的三个保障

① 规则优先：违禁词规则通道结论优先级高于任何模型输出；② 状态终态：veto 直接置“冻结”终态，业务接口无法改写；

③ 中断留痕：同步发 interrupt 并把证据包送人工，审计日志可回溯到命中的具体词条。

　03　存在的问题　

链路跑通后，质量与体验层面的问题开始浮现：

●　问题 1　规则与模型结论冲突的合并策略：目前模型驳回但规则通过时取保守结论，误杀率可能偏高，需要引入置信度差值阈值而不是简单取严。

●　问题 2　置信度缺少校准：RuleLLM 的 0.5/0.7/1.0 是经验值，模型自报置信度也未必准确，后续要用剧本批量结果做校准。

●　问题 3　建议价样本太少：种子历史成交价仅覆盖教材、自行车等几个类目，部分类目样本不足只能不建议，需要扩充种子数据。

●　问题 4　LLM 延迟影响体验：实测含模型的单轮平均 1.8 秒、高峰偶发超 3 秒，议价室需要“思考中”状态与超时自动降级联动。

●　问题 5　检查点库增长：长线程全量快照使 checkpoints.db 增长偏快，需要设置快照保留窗口。

●　问题 6　意图澄清话术偏生硬：缺槽追问目前是模板句子，计划在提示词中加入更自然的多轮澄清示例。
