　01　本周学习笔记　

本周承接第 1 周的顶层方案，学习主线从“概念扫盲”转向“工程落地”：围绕 UML 动态建模、并发控制、议价参数化、LLM 结构化输出与 Rule + LLM 双引擎五条线展开，并系统练习了“冲突剧本测试法”，把第 1 周的机制草图推进为可讨论、可验证的详细设计雏形。主要学习内容归纳如下。

1.1 UML 动态建模：时序图与活动图

● 两类图的分工：时序图回答“谁在什么时间、给谁发了什么消息”，活动图回答“在什么条件下走哪条分支”；前者用来验证消息闭环，后者用来验证判定逻辑，二者不能互相替代。

● 时序图四要素：生命线、激活条、同步/异步消息与组合片段（loop / alt / opt）；议价的多轮还价天然对应 loop 片段，冲突三级阶梯对应 alt 分支。

● 对本项目的价值：本周用时序图把九个 Agent 的主链路消息一一对位，立刻发现“议价 Agent 在出价之前必须先拿到信用风险意见”这一隐藏依赖，及时补进了流程设计。

1.2 并发控制：悲观锁、乐观锁与锁租约

● 悲观锁与乐观锁：悲观锁先加锁再操作，强一致但并发度低；乐观锁不加锁、提交时用 version 版本号校验，冲突稀少的 Web 场景吞吐更高。本项目确定采用“乐观版本号 + 短期预占锁”的组合方案。

● 锁租约（Lease）：任何锁都必须携带到期时间，持有者靠心跳续约，超时由系统回收，从机制上消灭“锁住商品却永不付款”一类的死锁与资源占用。

● 状态机是最后闸门：无论锁如何流转，商品与订单的状态迁移都集中到状态机校验，非法迁移一律拒绝，形成“预占锁 + 版本号 + 状态机”三重一致性保障。

1.3 议价策略的参数化：让步曲线与时间压力

● 让步三原则：单调性（买家只加价、卖家只降价）、有限轮次、时限内收敛；任何违反单调性的出价直接拒收，这一规则后来固化为下周异常码 E-301 的判定依据。

● 时间压力函数：越接近截止时间让步幅度越大，模拟真实“急着出手”心理；同时约定首轮大幅让步、末轮保底不让，避免被对方在两三轮内探到底价。

● 参数经验初值：单个议价会话最多 6 轮、总时限 120 秒、首轮让步不超过可行区间的 20%；纳什参考价借助历史成交价与已报价格轨迹估计，真实底价仍不可知。

1.4 LLM 提示工程与结构化输出

● 结构化输出三件套：JSON Schema 约束、Function Calling 固定字段、few-shot 示例对齐口径，让模型直接产出可被程序消费的对象，而不是一大段无法解析的散文。

● 输出不稳定的根因：温度采样、提示词歧义、长上下文注意力稀释；工程对策是低温度运行、字段级枚举约束与“解析即校验”，不让非法对象进入业务层。

● 三段式容错：解析失败先带因重试（把错误原因回传给模型自纠），重试仍失败则降级为规则引擎产出，任何分支都不允许脏结果写入交易状态。

1.5 Rule + LLM 双引擎结合模式

● 分工原则：确定性边界交给规则（状态校验、违禁词、让步单调性），开放性判断交给大模型（意图理解、纠纷归因、议价话术）；关键动作在模型产出后必须再过一遍规则后置校验。

● 无 Key 可降级：规则引擎从一开始就按 LLM 的“平替兜底”来设计而非临时补丁，无 API Key 的环境下全链路仍可跑通合法流程，为后续无 Key 回归测试预留条件。

1.6 冲突剧本测试法（Scenario-Based Testing）

● 剧本四要素：前置状态、触发事件、期望处置路径、期望终态；一个好剧本必须能判“通过 / 不通过”，而不是凭“看起来差不多”验收。

● 正常链路只能证明系统“能跑”，冲突剧本才能证明机制“有效”。本周据此把第 1 周的 8 个冲突场景扩写为 C1—C10 共 10 个可执行剧本，作为机制规则清单与自动化测试的种子用例。

2.4 并发抢单一致性方案设计（本周核心成果）

针对第 1 周遗留的“锁粒度、超时释放、支付失败回滚均不清晰”问题，本周设计“状态机 + 乐观版本号 + 带租约预占锁”三重保障，并对商品非在售、他人抢单失败、支付超时、回调冲突四种分支逐一给出回退路径，完整流程如图 2。

图 2 并发抢单一致性方案：三重保障与超时 / 冲突回退路径

● 锁粒度：锁加在“商品”而不是“订单”上——同一商品同时只允许存在一个待支付订单；lock_token 标识持锁订单，lock_until 规定 120 秒租约，到期由定时任务扫描释放。

● 乐观更新：加锁与支付回写均执行 UPDATE … WHERE id = ? AND version = ?，影响行数为 0 即说明已被他人抢先，从数据库层杜绝两个订单同时成交。

● 三条回退路径：商品非在售直接拒绝并推荐同类商品；抢单失败者秒级收到 E-201 异常码；支付超时自动取消订单并释放锁；极小概率的支付回调冲突则回滚支付、升级二级协调仲裁。

事件 商品状态变化 锁 / 版本动作
买家下单（商品在售） 在售 → 被锁定 写入 lock_token 与 lock_until，version 不变
120 秒内支付成功 被锁定 → 已成交（终态） version+1 条件更新，注销锁令牌
支付超时未完成 被锁定 → 在售 租约到期自动释放，订单置为已取消
并发买家同时下单 维持原状，仅一方可见锁定 条件更新失败方收到 E-201，不产生订单
成交后重复发起请求 终态拒绝迁移 状态机直接拦截并记录异常请求

◆ 锁机制三原则

① 锁必带租约，到期自动释放，杜绝“锁而不付”；② 一切状态写操作携带 version 条件，并发冲突靠数据库返回影响行数判定；③ 终态不可变，已成交商品的任何后续写请求都被状态机拒绝——三者缺一，“同一商品重复成交”就仍可能发生。

　03　存在的问题　

本周把第 1 周“凭感觉”的决定逐一逼到了要给字段、给参数的程度，复盘后梳理出以下尚待解决的问题：

● 问题 1　角色卡片仍是“自然语言契约”：输入输出只用文字描述，字段名、类型、枚举取值均未定义，下周必须用 Pydantic 固化，否则前后端无法并行开发。

● 问题 2　异常码尚未体系化：目前只有 E-201（预占失败）、E-301（让步违例）等零散几个，通信、审核、仲裁类编码还没有分段规划。

● 问题 3　数据库设计完全空白：11 张表还只是业务调研时记下的名词清单，字段、外键、唯一约束、乐观锁列均未落表。

● 问题 4　议价参数缺少数据校准：6 轮、120 秒、首轮 20% 让步上限均为经验初值，纳什参考价依赖用户私有底价，估计偏差对成交率的影响尚无法实验。

● 问题 5　框架选型仍停留在文档判断：LangGraph 的条件边、检查点、人工中断是否顺手，至今没有写过一行实测代码，不能只凭资料拍板。

● 问题 6　时序图与实现技术尚未对位：三级人工兜底节点如何用 LangGraph interrupt 挂起与恢复、ACL 消息如何持久化，机制还不清楚。

● 问题 7　剧本期望多为定性描述：C1—C10 目前只能验收“走到哪一级、终态是什么”，议价 P95 延迟、并发规模、成交率等量化指标要等原型跑起来后补齐。
